Project responsibilities and foundations

Camera capture, processing queues, and a desktop interface around person detection.

OpenCV supplies the pretrained HOG + SVM detector; Tkinter supplies the GUI. No custom-trained detector is claimed.

The problem

Camera acquisition and person detection proceed at different rates. Running detection on every captured frame can build a backlog and make the displayed scene stale. This prototype separates capture and processing into worker threads.

Processing budget

Bound the queue, reduce the workload

The queue holds at most five frames and drops incoming frames when full. Detection runs on every third consumed frame, resized to 400 pixels wide. Bounding boxes and a Windows audio alert expose detections to the user.

A concrete speed–coverage trade-off

Skipping detection and resizing input reduce work, but can miss brief appearances and small people. Dropping incoming frames bounds memory while retaining older queued frames, so it does not guarantee the freshest frame. A latest-frame strategy is a useful comparison.

Delivered / Prototype pipeline

Capture, detection, annotation, start/stop controls, and alerts are implemented. The repository contains no measured frame rate, latency benchmark, or detection-accuracy evaluation.

What I would change next

Move Tkinter updates onto the main thread, make camera failure visible, and replace the Windows-specific alert behind a platform adapter. Benchmark capture-to-display latency and false detections on recorded clips before claiming real-time performance. This uses a pretrained detector; it is not a custom-trained vision model.
