Quadmates

From a list of students to an accepted study request and a conversation.

Project responsibilities and foundations

Product direction and the discovery-to-session workflow. The case study covers matching rules, requests, and conversation behavior.

React handles the interface; Supabase supplies authentication, Postgres, storage, and realtime infrastructure.

The problem

A shared course is a useful starting point, but a study partnership also needs compatible schedules, preferences, and a way to make contact. Quadmates brings discovery, requests, messaging, groups, and session coordination into one product.

Implementation focus

Make recommendations explainable

The compatibility function returns a score alongside shared courses, overlapping minutes, and shared study styles. The system can show the reasons behind a recommendation rather than presenting a score without context.

One product, distinct responsibilities

React client handles discovery and conversation state. Express routes check membership and persist messages. Supabase provides authentication, Postgres, storage, and broadcast events. Persisted history and realtime updates meet in the chat component.

A small, inspectable ranking model

Course overlap contributes up to 50 points, availability up to 35, and study style up to 15. Courses are normalized for case and whitespace; the components saturate at three shared courses, ten hours of shared availability, and two shared styles. This is a deterministic heuristic, with weights that can be inspected and revised.

Illustrative calculation from the function: two shared courses + five overlapping hours + one shared style → round(33.33 + 17.5 + 7.5) = 58/100. This is an example, not a user result.

Keep the write path separate from delivery

The message route stores a message before broadcasting it. The chat UI merges responses and broadcast events by message ID to avoid showing duplicates. Failed sends retain the draft and expose a retry action. Typing notifications are throttled to roughly one update per 1.8 seconds, reducing event traffic while preserving feedback.

Delivered in the repository

Compatibility scoring, request acceptance, direct and group message routes, notification deduplication, and a chat interface with retry and reconnect states are implemented.

The current frontend is React + Vite; the previous portfolio’s Next.js label was inaccurate. No adoption, retention, latency, or security-audit result is claimed here.

Trade-offs and next validation

Fixed ranking weights make behavior understandable, but they are not calibrated against completed study sessions. Pairwise availability overlap can double-count overlapping entries; input normalization and edge-case tests are useful next work. Message persistence and broadcast delivery are separate operations, so reconnect recovery needs end-to-end verification. Route-level checks alone do not establish the security of realtime subscriptions.

02 / Simulation / Comparative evaluation

TransitOps

A transit-operations testbed that makes dispatch decisions visible—and makes their consequences measurable.

PythonFastAPINext.jsSUMO / TraCIBaseline comparison
Status

Role / context

Project responsibilities and foundations

Transit dispatch scenarios, controller rules, and comparative evaluation. The replay below uses output from the reviewed engine.

FastAPI exposes the API; Next.js presents the interface; SUMO and TraCI provide a separate microscopic simulation path.

The problem

Transfer arrivals, traffic, vehicle capacity, and dispatch timing interact. A locally sensible rule, such as sending an extra bus toward anticipated demand, can still worsen service elsewhere. TransitOps models those interactions across a four-stop corridor.

Core decision

Compare policies under the same scenario

The API runs baseline and adaptive cases for 60 simulated minutes using seed 17 and the same input parameters. It returns metrics, event logs, and a timeline so that a result can be traced back to operating decisions.

Two simulation paths

The Python corridor model advances passenger queues, vehicles, and dispatch in minute steps; FastAPI exposes the comparison to the web interface. A separate SUMO / TraCI path steps microscopic traffic, applies signal-priority actions, and produces vehicle and signal telemetry. They are distinct models, not interchangeable evidence.

Adaptive rules with explicit conditions

The corridor engine combines scheduled dispatch every ten minutes with demand-based pre-staging. It looks ahead to transfers and compares demand with arriving capacity. Signal priority requires a delayed, sufficiently occupied bus. The separate TraCI controller uses a 70 m approach threshold and a 15-second cooldown per signal.

Result / A hypothesis to revise

The adaptive case increased average wait by 1.70 minutes using unrounded values, and left 25 more passengers waiting. More interventions did not produce better service in this scenario.

Inputs: traffic multiplier 1.25, train delay 5 minutes, transfer demand 135, fleet size 4. Both cases generated 497 passengers. One scenario does not establish performance across a network.

What this comparison changes

The next experiment should isolate pre-staging and signal priority, sweep demand and traffic conditions, and compare multiple seeds. Average wait here includes passengers who boarded, so it must be read alongside the queue remaining at the end. This prevents a policy from looking good simply because hard-to-serve passengers never boarded.

Scope and reproducibility

The corridor model uses synthetic demand and simplified travel times; it is not calibrated to an operating transit agency. SUMO telemetry projects a synthetic corridor onto geographic anchors. The result table comes from the corridor engine, not the SUMO path. A reproduction script is included in this change’s review materials.

03 / Fleet state machine / Physical design constraints

TransitOps-M

A miniature fleet concept with software rules for reserving a depot bay, confirming arrival, and recovering from a stop.

Project responsibilities and foundations

Depot workflow, state transitions, and the interface between software rules and physical-layout constraints.

Python dataclasses represent fleet state; FastAPI serves the dashboard; FreeCAD macros generate concept geometry.

The problem

A command to return to a depot is not evidence that a vehicle has arrived. The dispatcher distinguishes a reserved bay from an occupied bay, and requires a separate confirmation before treating docking as complete.

Design boundary

Test the logic before connecting hardware

The dispatcher is independent of motors, sensors, and charging. A caller injects mock docking confirmation; the dashboard exposes simulation state. Physical integration remains future work.

Reservation and occupancy are separate state

Request depot: check availability, reserve the automated bay, mark the bus returning. Confirm docked: require a matching reservation and clear interlock, then assign occupancy. Dispatch: verify occupancy and release the bay.

Recovery must be deliberate

An emergency stop faults moving vehicles and clears reservations. Clearing the interlock does not resume motion: a faulted bus must be reset to holding. This encodes recovery as an explicit operator action rather than an incidental consequence of clearing a flag.

Verification / 8 existing tests passed locally

The suite covers station tracking and dwell, simulation reset, depot flow, double-booking rejection, safe stop, docking confirmation, and invalid tick counts. These checks establish modeled behavior, not physical safety.

CAD reveals a different set of constraints

The Depot B macro studies two active lanes and three staging slots on a 280 × 280 mm slab. The current dispatcher models one automated bay and two static parking bays, so the CAD and software capacities are not yet aligned. The CAD notes also identify 44 mm active lanes against an approximately 50 mm straight-road planning reference; swept paths and the selected chassis still need validation.

Next integration milestone

Agree on one depot configuration, reconcile the software and CAD, then implement a sensor adapter that can distinguish requested, confirmed, and faulted transitions. The present design has no real motor or charging control and is not fabrication-ready.

NeuroSim 2.0

Project responsibilities and foundations

A landing-environment experiment connecting state, control actions, reward design, and outcome-based evaluation.

Gymnasium defines the environment interface; Stable-Baselines3 supplies PPO. This project does not implement PPO from scratch.

The problem

A landing controller must manage position, speed, attitude, and fuel together. A training reward summarizes those objectives, but it can conceal undesirable behavior. The repository separates the environment, training loop, evaluation script, and viewer.

Model interface

Eight observations, three declared actions

Normalized observations describe position, velocity, attitude, fuel fraction, and target offset. The action space declares throttle, gimbal, and RCS commands. Planet and vehicle presets make the environment configurable.

Reward is not the success criterion

PPO learns from changes in a shaping function with fuel and RCS-command penalties. Touchdown success separately requires bounded position error, horizontal and vertical speeds, tilt, and angular rate. Evaluation records outcomes rather than relying on reward alone.

Design for repeatable evaluation

The evaluator defaults to 100 deterministic-policy episodes beginning at seed 10000, and writes per-episode CSV plus summary JSON. It reports success, crash and timeout rates, touchdown error, fuel use, and mean reward. This is an evaluation interface; held-out status still depends on keeping the training seeds separate.

Current result / Implementation incomplete

The reviewed environment does not parse: a literal backslash-n appears in the info dictionary at line 114. The RCS command is penalized and recorded but does not enter the dynamics, despite tests expecting it to change rotation.

No model checkpoint or evaluation output is committed in this snapshot. A landing-success percentage cannot be substantiated from this repository.

Next milestone: validate the environment first

Repair the syntax, implement and verify RCS torque, and run the existing environment tests before training again. Then evaluate a versioned checkpoint across fixed seeds and compare outcomes with reward. The physics are intentionally simplified; this is software experimentation, not validated flight control.

06 / Full-stack operations / Quadmates internal tool

Staffflow

An internal control plane for people, hiring, assessments and operational work.

ReactExpressSupabase PostgresResendRole-based access

The problem

Quadmates required a reliable way to track applicants, onboard contributors, review hours, manage shifts, and coordinate small-team projects without distributing everything across spreadsheets and email.

Architecture

One controlled backend

The React UI calls authenticated Express routes. Server-side permissions protect operations while Supabase stores staff, shifts, documents and audit events. Private storage is kept behind signed access.

Candidate evaluation without unsafe code execution

The assessment library supports deterministically scored code-reading templates and human-reviewed practical work samples. Candidate responses are persisted and server-enforced deadlines help prevent client-side timer bypass. Applicant code is never executed by the application server.

Make coordination observable

The dashboard surfaces approvals, blocked projects, onboarding tasks and notifications. Failed data loads are shown as unavailable rather than misleading zeros. The scheduling workflow supports shift edits and an agenda view.

Code-reviewed capabilities

Hiring pipelines, candidate access links, work check-ins, hours reporting, organization roles, and Supabase-backed data are present in the repository. Real-world usage, deliverability, scalability and security audit results are not claimed.

Trade-offs and what comes next

Candidate invitations initially required manual sharing. Automated email delivery is optional and must be configured. Assessment scoring is deliberately limited to safe, objective questions; a general-purpose code runner would require isolation. Multi-organization tenancy and enterprise-level access isolation are not yet established.

05 / Earlier perception project / Desktop prototype

Real-time person detection

A camera-to-interface pipeline built around OpenCV’s pretrained HOG + SVM person detector.

PythonOpenCVTkinterProducer / consumerBounded queue
Status
Earlier desktop prototype
Role / context
Personal vision project
Evidence reviewed
23 October 2026

Project responsibilities and foundations

Camera capture, processing queues, and a desktop interface around person detection.

OpenCV supplies the pretrained HOG + SVM detector; Tkinter supplies the GUI. No custom-trained detector is claimed.

The problem

Camera acquisition and person detection proceed at different rates. Running detection on every captured frame can build a backlog and make the displayed scene stale. This prototype separates capture and processing into worker threads.

Processing budget

Bound the queue, reduce the workload

The queue holds at most five frames and drops incoming frames when full. Detection runs on every third consumed frame, resized to 400 pixels wide. Bounding boxes and a Windows audio alert expose detections to the user.

A concrete speed–coverage trade-off

Skipping detection and resizing input reduce work, but can miss brief appearances and small people. Dropping incoming frames bounds memory while retaining older queued frames, so it does not guarantee the freshest frame. A latest-frame strategy is a useful comparison.

Delivered / Prototype pipeline

Capture, detection, annotation, start/stop controls, and alerts are implemented. The repository contains no measured frame rate, latency benchmark, or detection-accuracy evaluation.

What I would change next

Move Tkinter updates onto the main thread, make camera failure visible, and replace the Windows-specific alert behind a platform adapter. Benchmark capture-to-display latency and false detections on recorded clips before claiming real-time performance. This uses a pretrained detector; it is not a custom-trained vision model.
